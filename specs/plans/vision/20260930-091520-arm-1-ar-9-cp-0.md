## Goal

When both downstream tasks are complete, opening or saving a project populates a deduplicated,
10-entry, most-recent-first list surfaced identically in the File ▸ Récents submenu and on the
empty-state screen, with entries pointing at a now-missing file removed on the next read or on a
failed open — without touching `libs/project_io` or any line outside the functions S11 already owns.

### Assumptions
- **ASM-001**: the dedup key for `addRecentFile` is `QFileInfo(path).canonicalFilePath()`, falling
  back to the raw string when the file does not resolve (should not happen in practice: this
  function is only ever called from `setCurrentProjectPath` with a path that was just written or
  just successfully opened) -- *Why*: canonical paths collapse the same file reached via a symlink
  or a relative/absolute variant, which a plain string compare would treat as two entries -- Confidence: HIGH.
- **ASM-002**: `pruneMissingRecentFiles` tests existence with `QFileInfo(path).exists()`, matching
  the architecture's "chemins disparus" wording literally (existence, not readability) -- *Why*:
  distinguishing "missing" from "exists but unreadable/corrupt" is exactly why `openProjectFile`'s
  failure branch ALSO does a direct, unconditional `recentFiles_.removeAll(file)` on any load
  failure, independent of `pruneMissingRecentFiles` -- Confidence: HIGH.

### Open Questions
None — ARCH-RECENT-FILES/ARCH-MAINWINDOW-RECENTS/ARCH-EMPTYSTATE fully determine the API shape,
the insertion points, and the failure-purge behavior; the only gap this plan had to close itself is
the reentrancy mitigation below (EVIDENCED, not an open question — see Invariants).

**EVIDENCED correction of a cited precedent**: ARCH-MAINWINDOW-RECENTS justifies the
`confirmDiscardChanges(...)` guard on a Récents click as "même garde HP-FILE-001 que `loadProject`".
Direct inspection of `apps/desktop/main_window.cpp` (current `loadProject`/`openProjectFile`,
`rg confirmDiscardChanges`) shows `loadProject()` calls neither `confirmDiscardChanges` nor any
equivalent guard today — only `newProject()` (main_window.cpp:882) and `closeEvent`
(main_window.cpp:1310) do. The architecture's cited precedent does not exist, but the decision
itself (guard a Récents click, since it silently replaces the current document exactly like
`newProject` does) is independently reasonable and is kept exactly as specified in
ARCH-MAINWINDOW-RECENTS; Task 1 below implements the guard on that basis, not on the (incorrect)
"already how `loadProject` behaves" claim.

### Invariants and Review Checks
- **Reentrancy (the exact finding from the prior review round on this task)**: `refreshRecentFilesUi()`
  clears and rebuilds `recentMenu_`'s `QAction`s and `emptyState_`'s `QPushButton`s. Both new call
  sites that can run *while a `QAction`/`QPushButton` created by a previous `refreshRecentFilesUi()`
  call is still unwinding its own `triggered()`/`clicked()` handler* — i.e. `setCurrentProjectPath`
  (reached via `openProjectFile` reached via a Récents click) and `openProjectFile`'s failure branch
  (reached directly via a Récents click on a now-missing file) — MUST call `refreshRecentFilesUi`
  through `QTimer::singleShot(0, this, &MainWindow::refreshRecentFilesUi)`, never synchronously.
  This is the same one-event-loop-cycle deferral idiom already used in this file for exactly this
  class of self-referential-callback hazard (`main_window.cpp:6559-6562`, comment: "différé d'un
  cycle d'événements, comme elles"). The constructor's one-time initial call and `buildMenus()`'s
  menu creation are NOT inside any click chain and stay direct/synchronous. A reviewer should grep
  the diff for `refreshRecentFilesUi()` and confirm every call site outside the constructor goes
  through `QTimer::singleShot(0, this, ...)`.
- `recentMenu_`'s `QAction`s and `emptyState_`'s recent buttons are always rebuilt together, from
  the same `pruneMissingRecentFiles(loadRecentFiles())` result, inside `refreshRecentFilesUi()` —
  never populated independently, so the two surfaces cannot drift.
- `recentFiles_.removeAll(file)` in `openProjectFile`'s failure branch runs unconditionally on every
  failed open, not only when the failed path is known to have come from the Récents menu/list.
- No line outside the five named edit points in `main_window.cpp`/`.hpp` changes; `libs/project_io`
  and `resetDocumentState()` are untouched (per PARENT-S11's function-ownership table: S11 owns
  `setCurrentProjectPath`/`openProjectFile` entirely, but not `resetDocumentState`).

   with the newest first and the oldest dropped; (b) adding a path already present (including via a

   `window.recentMenu_->actions()` has exactly 2 entries in the same order.
3. A new Qt test slot repeats the two-save setup above, deletes the older temp file from disk with
   `QFile::remove`, then uses `QTest::mouseClick` on the corresponding recent-file `QPushButton`
   found under `emptyState_` (real click, not a direct `openProjectFile` call — this is the
   regression test for the reentrancy finding: it drives the exact
   `clicked()` -> lambda -> `confirmDiscardChanges` -> `openProjectFile` -> `setCurrentProjectPath`
   -> (deferred) `refreshRecentFilesUi()` chain through Qt's real button-activation code path,
   which is what actually tears down and rebuilds the very button mid-click if the deferral is
   missing), arms `autoDismissModalDialogs(&window)` beforehand for the expected
   `QMessageBox::warning`, processes events, and asserts the test process is still alive with
   `window.recentFiles_` now containing only the still-existing file.
4. `cmake --build --preset msvc-debug --target openstitch_desktop_widgets`, `ctest --preset
   msvc-debug -R main_window`, and `git ls-files '*.cpp' '*.hpp' | xargs clang-format --dry-run
   --Werror` all succeed.
